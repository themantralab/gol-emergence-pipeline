# GoL Emergence Discovery — Design Specification

> **⚠️ SUPERSEDED (historical record).** Describes the *hypershell* latent design,
> replaced by the vanilla autoencoder after it hit a ~0.74 reconstruction ceiling.
> See [`03_final_architecture.md`](03_final_architecture.md) and the repo README for
> the current trained model. Retained for the record.

## System overview

A dual-model system for unsupervised discovery of emergent behaviour in Conway's Game of Life.

- **World Model**: encodes GoL frames into a structured latent geometry. Produces a Z library of encoded trajectories.
- **Explorer Model**: navigates the Z library, identifies frontier regions, proposes novel trajectories, validates them against the GoL engine, expands the library.

The world model is implemented first. The explorer is designed but not yet implemented — the world model must provide headroom for it.

---

## Data

- 128×128 binary grids
- 16×16 random seeds embedded at fixed offset (24, 24)
- Trajectories of length k (typically k = 256) generated by the GoL B3/S23 rule
- Each trajectory is a sequence of frames [f₀, f₁, ..., fₖ]
- Dead-to-alive ratio approximately 378:1

A pre-generated dataset of 1.5M seeds with lifespan/bucket stratification metadata already exists. See `../DATASET.md` for exactly which files the model consumes versus which are retained for future expansion or external diagnosis. The model's direct inputs are the **seed corpus** (`seeds.npy`, the source of every training trajectory) plus the **stratification metadata** (`lifespans.npy`, `buckets.npy`, read by the stratified batch sampler). Trajectories themselves are produced by simulating seeds through the GoL engine at training time; nothing else in the dataset is on the training path.

## World Model

### Architecture

**Encoder**
- Input: 128×128 binary grid
- Architecture: CNN with progressive downsampling, then flatten, then linear projection, then L2 normalisation
- Output: unit direction vector û ∈ S^(d-1) where d = 256
- **No centroid subtraction.** Spatial position is signal and must be preserved.
- **No shell index input.** The encoder is shell-agnostic.
- **No global pooling.** Flatten preserves spatial arrangement.

```python
class Encoder(nn.Module):
    def __init__(self, d=256):
        super().__init__()
        self.conv = nn.Sequential(
            nn.Conv2d(1, 32, 3, stride=2, padding=1), nn.GELU(),   # 64×64
            nn.Conv2d(32, 64, 3, stride=2, padding=1), nn.GELU(),  # 32×32
            nn.Conv2d(64, 128, 3, stride=2, padding=1), nn.GELU(), # 16×16
            nn.Conv2d(128, 256, 3, stride=2, padding=1), nn.GELU(),# 8×8
        )
        self.project = nn.Linear(256 * 8 * 8, d, bias=False)

    def forward(self, grid):
        h = self.conv(grid)
        h = h.flatten(1)
        z = self.project(h)
        return F.normalize(z, dim=-1)
```

**Decoder**
- Input: unit direction û (radius is irrelevant to the decoder)
- Output: 128×128 logits
- Loss: BCE with pos_weight=50 to handle class imbalance

```python
class Decoder(nn.Module):
    def __init__(self, d=256):
        super().__init__()
        self.project = nn.Linear(d, 256 * 8 * 8)
        self.deconv = nn.Sequential(
            nn.ConvTranspose2d(256, 128, 4, stride=2, padding=1), nn.GELU(),
            nn.ConvTranspose2d(128, 64,  4, stride=2, padding=1), nn.GELU(),
            nn.ConvTranspose2d(64,  32,  4, stride=2, padding=1), nn.GELU(),
            nn.ConvTranspose2d(32,  1,   4, stride=2, padding=1),
        )

    def forward(self, z):
        h = self.project(z).view(-1, 256, 8, 8)
        return self.deconv(h)
```

**There is no transition function.** The GoL engine is the simulator. The world model only encodes and decodes; it does not predict.

### Hypershell geometry

The latent space is structured as nested hypershells in ℝᵈ:

- Each shell n is a full S^(d-1) at radius rₙ = r · (n+1) for some constant r
- A frame fₙ at time step n is mapped to z_n = û_n · rₙ, where û_n = encoder(fₙ)
- The radius is applied externally after encoding. The encoder produces only the unit direction.
- A trajectory is a sequence of points in ℝᵈ, one per shell, with shell membership implicit in row index

### Losses

Four losses on the world model. No others.

**L₁ — Reconstruction** (weight 1.0)
BCE with positive class weighting to handle the 378:1 dead-to-alive imbalance.
```python
loss_recon = F.binary_cross_entropy_with_logits(
    decoder(û), target_grid, pos_weight=torch.tensor([50.0])
)
```

**L₂ — Encoder smoothness** (weight 1.0)
Forces angular distance in latent space to correlate with mechanical distance in grid space. The mechanical distance metric is **normalised Hamming distance** (pixel-wise XOR count over total cells) — the natural complement to BCE on binary grids, operating directly on the grid representation without requiring coordinate extraction.

The naive `MSE(cosine_dist, hamming_dist)` formulation has a scale problem: within-trajectory Hamming distances are typically 0.001–0.006 (10–100 cells of 16,384), while cross-trajectory Hamming distances are 0.05–0.30 — a 50–100× scale gap. Under raw MSE the cross-trajectory residuals dominate by 2500–10000×, starving the near-end of gradient and defeating the "local smoothness" the loss is meant to provide. Two refinements address this:

1. **Sqrt-scale the Hamming target** so small differences get meaningful weight (1-pixel diff goes from 0.000061 → 0.0078). Sqrt is monotonic, so angular distance still tracks mechanical distance, just non-linearly.
2. **Compute within- and cross-trajectory sub-losses separately** and average, so the optimiser spends equal attention on both regimes regardless of their absolute scale.

```python
def hamming_distance(grids_a, grids_b):
    # grids: (B, 1, 128, 128) binary float tensors
    diff = (grids_a != grids_b).float()        # XOR
    return diff.sum(dim=[1, 2, 3]) / (128 * 128)  # (B,) normalised [0, 1]

def cos_dist(u_a, u_b):
    return (1 - (u_a * u_b).sum(-1)) / 2       # (B,) normalised [0, 1]

def smoothness_subloss(grids_a, grids_b, encoder):
    u_a, u_b   = encoder(grids_a), encoder(grids_b)
    target     = torch.sqrt(hamming_distance(grids_a, grids_b))
    prediction = cos_dist(u_a, u_b)
    return F.mse_loss(prediction, target)

def smoothness_loss(within_pairs, cross_pairs, encoder):
    L_within = smoothness_subloss(*within_pairs, encoder)
    L_cross  = smoothness_subloss(*cross_pairs,  encoder)
    return (L_within + L_cross) / 2
```

Pair construction: each batch contains both **within-trajectory pairs** (two random frames from the same chain, small Hamming) and **cross-trajectory pairs** (two random frames from different chains, large Hamming). This range coverage is essential — within-only pairs would let the encoder collapse everything close; cross-only pairs would let it scatter maximally. Both ends are needed to learn the slope of the calibration.

**L₃ — Chain clustering** (weight 1.5, must dominate)
NT-Xent contrastive on trajectory-level fingerprints. Fully self-supervised: positive pairs are two non-overlapping subsamples of frames from the same trajectory; negative pairs are subsamples from different trajectories.

```python
def chain_fingerprint(directions, n_samples=32):
    # directions: (k+1, d) unit vectors
    idx = torch.randperm(directions.shape[0])[:n_samples]
    idx = idx.sort().values  # preserve temporal order
    return directions[idx].flatten()  # (n_samples * d,) fingerprint vector

def chain_clustering_loss(batch_directions, tau=0.1):
    # batch_directions: list of B trajectories, each (k+1, d)
    fps_a = torch.stack([chain_fingerprint(d) for d in batch_directions])
    fps_b = torch.stack([chain_fingerprint(d) for d in batch_directions])
    fps_a = F.normalize(fps_a, dim=-1)
    fps_b = F.normalize(fps_b, dim=-1)
    sim = fps_a @ fps_b.T / tau
    labels = torch.arange(len(batch_directions))
    return F.cross_entropy(sim, labels)
```

Intuition: two random subsamples of the same trajectory should produce similar fingerprints (positive pair); subsamples of different trajectories should produce different fingerprints (negative pair). No labels needed — same-trajectory identity is the supervision signal. Similar trajectories naturally cluster because their fingerprints come out similar regardless of which subsamples are drawn.

**L₄ — Hyperspherical uniformity** (weight 0.3)
Prevents collapse without imposing Gaussian/isotropic pressure. Computed over all unit directions in the batch.
```python
def uniformity_loss(z):
    # z: (B, d) unit vectors
    sq_dist = 2 - 2 * (z @ z.T)
    return torch.log(torch.exp(-2 * sq_dist).mean())
```

Total loss:
```
L_total = L₁ + 1.0·L₂ + 1.5·L₃ + 0.3·L₄
```

### Z library storage

Per trajectory, store:
```python
{
    'directions': tensor of shape (k+1, d) dtype=float16,   # one unit vector per frame
    'seed':       binary 16×16 array      dtype=uint8,      # ground-truth seed
}
```

Trajectory length k is read from `directions.shape[0] - 1`. Shell radii are computed when needed via `r * (n+1)`. No metadata scalars.

**Confirmed locked (2026-06-01): seed is always stored.** 32 bytes per trajectory is negligible insurance against decoder drift and gives a ground-truth anchor for reconstruction evaluation. The seed could in principle be recovered by decoding `directions[0]` and cropping to the 16×16 embedding region, but decoder reconstructions are approximate; exact reproducibility (bit-perfect re-simulation) requires the original bytes.

**Confirmed locked (2026-06-01): directions stored as float16.** Angular precision on the unit sphere at 16-bit is far more than enough. Storage estimate for the full 1.5M-trajectory Z cloud at k=256: `1.5M × 257 × 256 × 2 bytes ≈ 193 GB` (half the float32 cost). Fits comfortably in available disk (2 TB).

## Explorer Model

The explorer is not implemented in this initial build. The world model must provide sufficient structure for the explorer to be implemented later. Required properties of the latent geometry:

- Behavioural classes form distinct angular regions on each shell
- Frontier regions are identifiable as low-density boundaries of known clusters
- The transition function is NOT learned — the GoL engine is the validator

### Explorer design (for context, not implementation)

The explorer will eventually:
1. Propose a starting direction û₀ at shell 0 in a frontier region of the angular distribution
2. Decode û₀ to a 128×128 grid
3. Hand the grid to the GoL engine, which produces the full trajectory
4. Encode each resulting frame to produce the actual chain
5. Verify mechanical validity: û₀_proposed ≈ û₀_actual
6. Check novelty against the Z library using five mechanisms:
   - Per-shell angular distance
   - Chain signature distance (Δθ sequence, return similarity, decay)
   - Density estimator (normalising flow on S^(d-1))
   - Topology novelty (unfamiliar period, drift, decay profile)
   - Reconstruction error gap
7. If accepted, add to Z library and refit density model

## Training protocol

Single phase. All four losses active from the start.

**On curriculum:** the previous version of this system used a curriculum on rollout horizon k_max, because it had a transition function that needed to be trained at progressively longer horizons. The current design has no transition function — the encoder processes each frame independently and the GoL engine produces the full trajectory in one shot. There is no rollout to curriculum. Trajectories are encoded at full length from the start. **Confirmed locked (2026-06-01): no curriculum.**

Recommended hyperparameters:
- d = 256
- batch size = 32 trajectories per batch
- LR = 3e-4
- Adam optimiser
- pos_weight = 50 for BCE
- λ₁ = 1.0, λ₂ = 1.0, λ₃ = 1.5, λ₄ = 0.3

## What the world model produces

After training:
- Trained Encoder weights
- Trained Decoder weights
- Z library: collection of (directions, seed) pairs, one per training trajectory
- The latent geometry on the hypershells

The Z library is the working substrate for the explorer.

## Open questions — status

1. **Shell radius constant r.** *Locked 2026-06-01: r = 1.* Shell n sits at radius n+1. No pipeline operation depends on a different scale.

2. **Smoothness loss pair sampling rate.** *Default 50/50 within- vs cross-trajectory pairs per batch.* Subject to re-tuning if Stage 3 diagnostics show angular distance collapsing or failing to distinguish nearby states.

3. **Chain fingerprint subsample size.** *Locked 2026-06-01: n_samples = 32.* Verify cosine self-similarity ≥ 0.9 averaged over held-out trajectories. If unstable, bump to 48; only drop to 24 after stability is confirmed at lower cost.

4. **Trajectory variation in the training set.** *Locked 2026-06-01: lifespan-quartile stratified sampling* on the kept training pool. Three coupled rules:
   - **Stratification key:** `lifespans.npy` quartiles, not the density bands in `buckets.npy`. Density doesn't correlate with behaviour; lifespan does — long-lived patterns (gliders, oscillators, spaceships) all sit in the upper lifespan quartiles, while ~20% of seeds die fast. Equal slots per lifespan quartile per batch boosts rare long-lived behaviours without using class labels (`labels.npy` stays diagnosis-only).
   - **Training threshold:** drop trajectories with `lifespan < 32` from the training pool (cannot supply 32 distinct live frames for a fingerprint). Keeps ~80% of the corpus (~1.2M trajectories).
   - **Fingerprint frame restriction:** L₃ subsamples 32 indices from `[0, lifespan]`, never from dead-region frames. Avoids the unminimizable case where two distinct dying trajectories produce identical all-zero frames → identical encodings → identical fingerprints → L₃ cannot separate them and wastes capacity trying.
   - **Z cloud coverage is unaffected:** Stage 5 encodes all 1.5M trajectories regardless of training threshold. Filtering only changes which trajectories influence the encoder's weights, not which end up in the searchable inventory.
